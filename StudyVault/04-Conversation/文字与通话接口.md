# 文字与通话接口

## 文字回合

先用 `POST /api/conversations` 建立属于自己的对话，body 为 `{"character_id":"mano"}`。返回 201 和该对话信息。再发送：

```http
POST /api/conversations/{conversation_id}/turns
Content-Type: application/json
Origin: <当前站点 Origin>
Cookie: <登录会话>
```

```json
{"text":"今天练习辛苦吗？"}
```

可以另带 `own_keys`，结构以 `OwnKeysInput` 和前端 LocalOwnKeys 的约定为准。旧字段 `own_llm` 会被 422 拒绝并要求刷新，不能照旧示例发送。

响应为 `text/event-stream`，每条记录是 `data: <JSON>` 后接空行。以下是独立事件的示意，不是按网络 chunk 边界解析的契约：

```text
data: {"type":"user","text":"今天练习辛苦吗？"}

data: {"type":"delta","segment":0,"lang":"ja","text":"はい"}

data: {"type":"delta","segment":0,"lang":"zh","text":"是的"}
```

| 事件 | 字段或用途 |
|---|---|
| user | 本轮接收的 text |
| photo | 生成中的 id、status=pending；可选 |
| delta | segment、lang=ja/zh、text；按段与语言累加 |
| photos-used-up | retry_at；可选 |
| done | message、affinity，可选 ended/rewarded；成功记录后发送 |
| error | message；流内失败，不是成功完成 |

前端要缓存跨 chunk 的不完整 SSE 行，不能每个 ReadableStream chunk 单独 JSON.parse。没有把 `SegmentComplete`、`SpeechDelta` 或 `TurnJudged` 发到文字流。

## 通话建立

| 方法 | 路径 | 数据 |
|---|---|---|
| GET | `/api/ice-servers` | 可带 own=llm,tts,stt 和 conversation；只列服务名称，不在 URL 放 key |
| POST | `/api/offer` | sdp、type、requestData；已有 pc_id 表示重协商 |
| PATCH | `/api/offer` | pc_id、候选列表 |

```json
{
  "sdp": "<browser-generated SDP>",
  "type": "offer",
  "requestData": {
    "conversation_id": "<owned-conversation-id>",
    "muted": false,
    "quality": "standard"
  }
}
```

requestData 是 Pydantic Offer.call 的别名。新通话缺少它返回 422；这不是向 turns 接口发送音频。信令应答用于创建连接，后续日中事件经 RTC data channel，音频经媒体轨；角色 emotion、speaking、ended 等不能当成普通 SSE 增量。

## 错误处理与客户端行为

| 状态 | 含义与字段 |
|---|---|
| 401 / 428 | 需要登录 / 同意条款；前端转页 |
| 404 | 无权或不存在的对话/通话资源 |
| 409 | 冷却可带 cooldown_until；已结束/重复拨号用 detail 区分 |
| 429 | 限额可带 retry_at，或一般外部服务节流；读取 Retry-After |
| 503 | 未配齐通话服务，或 code=calls_busy |
| 422 | body/own_keys 校验失败，或过时 own_llm 字段 |

> [!important] 验证边界
> 上表是当前源码契约，不表示本次真实调用成功。流内错误、已提交的历史、额度结算要分别读取；HTTP 200 与第一条 delta 都不是完整成功证明。
